# CheckStock

Веб-прототип учёта остатков на складах фулфилмента: где товар, сколько доступно,
что зарезервировано под FBS и что уже отправлено.

## Стек

Python 3.11 · FastAPI · SQLAlchemy 2 · PostgreSQL 16 · Alembic · Jinja2 · Bootstrap · Docker Compose

## Быстрый старт

```bash
docker compose up --build
```

Открыть:

- интерфейс — http://localhost:8080/stock
- документация API — http://localhost:8080/docs

При старте контейнер сам применяет миграции (`alembic upgrade head`) и заливает
тестовые данные (идемпотентно — повторный запуск дублей не создаёт).

## Тестовые данные

| Артикул | Товар | Север | Юг |
|---|---|---|---|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

## Что умеет

- **Остатки** — по каждому артикулу и складу: физически, резерв FBS, доступно;
  отдельный блок «В пути» (между ФФ, на FBO, к клиенту по FBS).
- **Приход** — увеличивает остаток выбранного склада.
- **Резерв FBS** — блокирует товар под заказ: физически он остаётся на складе,
  но становится недоступным для продажи и перемещения.
- **Отгрузка FBS** — снимает резерв, списывает товар со склада и переводит его
  в «Транзит FBS».
- **Перемещение между ФФ** — списывает с источника, переводит в «Транзит ФФ»;
  после **приёмки** товар появляется на складе назначения.
- **Склады** — добавление, переименование, удаление. Удаление мягкое: остатки
  и история сохраняются, склад помечается архивным.
- **История операций** — тип, товар, склад, количество, резерв.

## Сценарий проверки

1. Остатки → резерв 3 (SKU-101, Юг): физически 6, доступно 3.
2. Движения → отгрузка FBS 3 (SKU-101, Юг): Юг 3, «В пути FBS» 3.
3. Движения → перемещение 4 (Юг → Север): Юг 0, «Транзит ФФ» 4.
4. Перемещения → «Принять»: «Транзит ФФ» 0, Север 14.
5. Склады → удалить «Юг»: склад в архиве, остатки и история на месте.
6. Попробовать отгрузить без резерва — интерфейс объяснит, что нужно сначала
   зарезервировать товар.

Проверка целостности:

```sql
SELECT p.sku,
       (SELECT COALESCE(SUM(qty_delta), 0) FROM ledger   WHERE product_id = p.id) AS ledger_total,
       (SELECT COALESCE(SUM(physical),  0) FROM balances WHERE product_id = p.id) AS balance_total
FROM products p ORDER BY p.sku;
```

Столбцы должны совпадать: сумма всех движений равна сумме всех остатков.

## Ключевые решения

1. **Журнал как источник правды.** Все изменения — записи в `ledger` (`qty_delta`,
   `reserve_delta`), а `balances` — кэш для быстрого чтения. Поэтому всегда можно
   ответить «где товар» и пересчитать остатки с нуля.
2. **Транзитные локации вместо «невидимого» товара.** Перемещение и отгрузка
   создают пару проводок: `−` на источнике и `+` в транзитный бакет. Товар
   никогда не исчезает и не задваивается при агрегации.
3. **Идемпотентность на уровне БД.** Уникальный индекс `(kind, idempotency_key)`
   плюс `INSERT ... ON CONFLICT DO NOTHING`. Повторный запрос (двойной клик,
   ретрай после сбоя) возвращает результат первой операции и не меняет остатки.
   Ключ приходит от клиента — в API это заголовок `Idempotency-Key`, в интерфейсе
   скрытое поле, генерируемое при отрисовке страницы.
4. **Атомарная проверка остатка.** Резерв и отгрузка выполняются одним
   `UPDATE ... WHERE available >= qty RETURNING ...`. Если строк не вернулось —
   товара не хватает. Отдельный `SELECT` перед `UPDATE` оставлял бы окно для
   гонки двух менеджеров.
5. **Мягкое удаление склада.** `is_deleted = true`; остатки и история остаются,
   новые операции по складу блокируются. Данные не теряются.
6. **`server_default` для счётчиков и флагов.** Загрузка данных работает не только
   через ORM: прямые SQL-вставки и сиды не падают на `NOT NULL`.

## Ошибки API

| Код | Когда | Тело |
|---|---|---|
| 400 | нет заголовка `Idempotency-Key` | `{"detail": "..."}` |
| 404 | товар/склад/перемещение не найдены | `{"error": "not_found", ...}` |
| 409 | не хватает на складе | `{"error": "insufficient_stock", "requested", "available_here", "available_total", "can_move", "suggestion"}` |
| 409 | нельзя отгрузить | `{"error": "cannot_ship", "physical", "reserved", "reason"}` |
| 422 | невалидное тело (qty ≤ 0) | стандартный ответ FastAPI |

## Тесты

```bash
python -m pytest
```

Шесть тестов на отдельной базе `checkstock_test`: приход, резерв, отгрузка,
нехватка, идемпотентность и сверка журнала с балансами.

## Локальный запуск без Docker

```bash
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # Windows
pip install -r requirements.txt

# PostgreSQL на localhost:5432, база checkstock
alembic upgrade head
python -m scripts.seed
uvicorn app.main:app --reload
```

## Структура

```
app/
  config.py        настройки (DATABASE_URL)
  db.py            engine и сессия
  models.py        модели SQLAlchemy
  schemas.py       Pydantic-схемы API
  services/stock.py  вся бизнес-логика учёта
  routers/stock.py   REST API
  routers/pages.py   HTML-страницы
  templates/       Jinja2-шаблоны
migrations/        Alembic
scripts/seed.py    тестовые данные
tests/             pytest
```

## Ограничения прототипа

- нет авторизации и ролей;
- одна единица измерения на товар;
- FBS: доставка клиенту не подтверждается, товар остаётся в «Транзит FBS»;
- FBO: приёмка маркетплейсом не реализована;
- интеграции с Wildberries/Ozon — вне рамок прототипа.
